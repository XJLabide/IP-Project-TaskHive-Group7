# Hosted checkout sandbox verification

Production must use a configured provider; the unsigned fake provider is disabled in production. The checkout page is designed to send only a task ID to TaskHive before opening the provider's hosted checkout. A return from checkout is not payment confirmation: only a verified provider callback can activate an assignment.

Maya sandbox checkout is enabled only for local development and Vercel Preview. Production checkout remains disabled. Each checkout attempt is saved before contacting the provider. Idempotent providers reuse the saved key after a timeout; a database claim permits only one outbound call to a provider without guaranteed idempotency. Such an attempt moves to `RECONCILIATION_REQUIRED` after an ambiguous result and blocks retries. The database permits only one creating or active attempt per payment. Deploy the `20261118120000_payment_attempts` migration before running this version.

Verified callbacks that arrive before the provider reference is saved remain unprocessed and are replayed when that attempt is linked. A second successful attempt after a payment has already been recorded is marked `LATE`; it does not activate the assignment or create another payout. Support must reconcile and refund any second capture with the provider dashboard. Attempt rows and callback rows contain provider references, amounts, and statuses only; never store payment credentials or webhook secrets there.

Stripe and PayMongo receive the persisted UUID as an API idempotency key. Maya's Checkout API accepts it as `requestReferenceNumber` and recommends a unique value per transaction, but does not document that field as an idempotency guarantee. After an ambiguous Maya timeout, the attempt is blocked in `RECONCILIATION_REQUIRED`. Support must check the Maya dashboard before allowing another attempt: if checkout exists, attach its returned ID to the existing attempt; if it does not, mark that attempt failed and return the payment to unpaid. This sandbox adapter cannot automatically reconcile by request reference.

For Maya sandbox, the shared public test key is available in Maya's Developer Hub; no business signup is needed to try the sandbox. Set `PAYMENT_PROVIDER=maya` and `MAYA_MODE=sandbox` in your local environment or Vercel Preview. The adapter uses Maya’s published shared sandbox API key and both published sandbox webhook verification keys by default; override these in an untracked env file if Maya rotates them or provides account-specific sandbox values. Use a non-production database and disposable test tasks. Register the preview HTTPS callback at `/api/payments/webhook`; localhost webhooks require a temporary secure forwarder. For Maya sandbox only, returning to TaskHive also queries Maya’s authenticated status endpoint and reconciles a completed payment if the webhook did not arrive. Never rely on the redirect alone or put private keys or real payment credentials in fixtures, logs, or Git.

For Maya sandbox, verify:

1. Create a task and a pending-payment assignment as the Poster. Start checkout and confirm that the hosted URL belongs to the selected provider and no payment fields are collected by TaskHive.
2. Complete payment using only the provider's documented test method. Verify that the assignment remains pending until an authentic successful webhook is processed, then becomes active exactly once.
3. Exercise a declined payment and a cancelled checkout. Verify that neither activates the assignment, and that the Poster can see the failure or cancellation.
4. Redeliver the same successful webhook and verify that it does not activate the assignment twice or create an additional payout. Send an invalid signature and verify it is rejected.
5. Check the provider dashboard, TaskHive's payment and event records, and callback delivery logs for agreement. For a database-backed concurrency exercise, send two checkout requests for the same pending task at once; confirm both return the same hosted checkout and that `PaymentAttempt` contains only one `CREATING` or `CHECKOUT_STARTED` row for the payment. Replay two successful event IDs for that attempt and confirm the second is recorded as a duplicate, then exercise a distinct attempt captured after payment and verify it becomes `LATE`. Also exercise delayed and out-of-order callbacks before production use.

The repository tests use mocked gateway clients; they do not replace these sandbox checks. Maya documents shared sandbox keys and test cards in [About Maya Checkout](https://developers.maya.ph/reference/about-maya-checkout), the [Create Checkout API](https://developers.maya.ph/reference/createv1checkout), and [Webhook Security](https://developers.maya.ph/reference/webhook-security).
